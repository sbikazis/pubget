PUBGET REBIRTH — PROMPT 3
إعادة بناء نظام EVENTS بالكامل من الصفر
هذه المهمة مخصصة حصريًا لـ Events Domain.

هذه ليست Games.

هذه ليست امتدادًا للألعاب.

لا تستخدم Game Engine داخل Events.

لا تجعل Game نوعًا من Event.

لا تجعل Event نوعًا من Game.

1. تعريف النظام
Event في Pubget هو:

محتوى/نشاط اجتماعي تفاعلي يمكن للمستخدمين المشاركة فيه والتصويت والإجابة والنقاش، وليس لعبة.

Events يمكن أن تكون:

Group Event
Multi-Group Event
Global Event
هذه هي Scopes الوحيدة.

2. إنشاء Event
يوجد مساران فقط:

المسار الأول
Group Chat
↓
+
↓
Create Event
هذا ينشئ Event مرتبطًا بالمجموعة.

المسار الثاني
Home
↓
+
↓
Event
ثم يختار المستخدم Scope:

Global
Selected Groups
إذا اختار Selected Groups: يختار المجموعات التي هو عضو فيها والمسموح له بالنشر فيها.

لا تحتاج Events إلى موافقة Group Owner.

عند النشر: ينشر Event مباشرة.

3. Daily Creation Limit
كل مستخدم يستطيع إنشاء:

حد أقصى 2 Events في اليوم.

هذا الحد يشمل:

Global Events
Group Events
Multi-Group Events
ولا يهم عدد المجموعات التي نشر فيها نفس Event.

Event واحد متعدد المجموعات = Creation واحدة.

التحقق Server-side.

يجب منع race conditions.

7 أيام.

إذا لم يحدد المستخدم StartAt مستقبلية: يبدأ Event عند Publish.

View More

14. المعلومات أثناء Event
هناك 3 مستويات من المعلومات:

المستوى الأول — Public Live Information
المعلومات التي يمكن للجميع رؤيتها أثناء Event.

مثل:

عدد المشاركين
نسبة النتائج إذا كان النوع يسمح
الوقت المتبقي
المشاركة العامة
المستوى الثاني — Participant Information
المعلومات التي يحصل عليها الشخص الذي شارك.

المستوى الثالث — Creator Analytics
Creator يرى المعلومات التفصيلية التي تخص Event الخاص به، بما فيها:

من شارك
من اختار ماذا
النتائج
التوزيع
التفاعل
البيانات التفصيلية المتاحة لذلك النوع
هذه البيانات لا تكون متاحة للآخرين.

15. Event Result Notification
إذا شارك المستخدم في Event تفاعلي وانتهى:

يرسل له Notification.

عند الضغط:

يفتح Event Result Page.

تظهر:

Event
مشاركته
النتيجة النهائية
الإحصائيات
النتيجة الخاصة به
معلومات النهاية
هذا ينطبق على الأنواع التي لديها Participation/Result.

لا تطبق هذه القاعدة على Theory وOpen Discussion بالطريقة نفسها إذا لم يكن فيها Participation Result تقليدي.

16. POLL
Poll يسمح للCreator بطرح سؤال وخيارات.

يجب أن يدعم:

Single choice
Multiple choice
Creator يحدد النوع أثناء الإنشاء.

يجب تحديد عدد خيارات معقول، ولا تسمح بخيار واحد فقط.

كل Option يمكن أن يحتوي على:

Text
Optional Image
المستخدم يشارك من خلال UI واضح.

بعد التصويت:

يتم تسجيل اختياره.
لا يسمح بالـduplicate vote.
لا يمكن تغيير التصويت بعد إرساله في Pubget 1.0.

النتائج الحية تظهر كنسب/أعداد دون كشف أسماء المصوتين للعموم.

Creator يستطيع رؤية:

المستخدم
اختياره
17. QUESTION
Question Event هو سؤال تفاعلي لا يشترط وجود إجابة صحيحة.

Creator يكتب:

Question
Optional description
Optional image
Answer configuration
المستخدم يقدم إجابة.

الإجابة يمكن أن تكون:

Text
Optional Image
Question لا يتحول تلقائيًا إلى Quiz.

18. THEORY
Theory Event هو منشور نظرية.

Creator يكتب النظرية.

يمكنه إرفاق:

Images
Text
المستخدمون يستطيعون:

Comment
React/Like
Discuss
Share
لا يوجد Correct Answer.

لا يوجد Vote إلزامي.

لا يوجد Participation Result تقليدي.

عند انتهاء Event: تبقى النظرية محفوظة في Archive مع التعليقات والتفاعل.

19. COMPARISON
Comparison يسمح بمقارنة عناصر يحددها Creator.

يجب أن يكون الاختيار مرنًا بما يكفي للمحتوى المتعلق بالأنمي.

يمكن أن تكون المقارنة بين:

Characters
Anime
Abilities
Other valid anime-related entities
لكن Comparison العام لا يسمح بإدخال عناصر عشوائية بدون بيانات قابلة للعرض.

المستخدم يختار الطرف الذي يفضله.

النتيجة تعرض:

Votes
Percentages
Winner
20. CHARACTER COMPARISON
نوع متخصص للمقارنة بين شخصيات Anime.

Creator يبحث عن Character من Character Database.

يختار شخصيتين.

المستخدم يصوت لصالح إحدى الشخصيتين.

يمكن إرفاق:

Character image
Name
Anime
النتيجة:

Votes
Percentages
Winner
21. ANIME COMPARISON
نفس الفكرة لكن بين Anime.

Creator يختار:

Anime A Anime B

المستخدم يصوت.

النتيجة:

Votes
Percentage
Winner
22. RANKING
Creator ينشئ قائمة عناصر.

مثلاً Anime/Characters.

المستخدم يرتب العناصر حسب تفضيله.

استخدم Drag & Drop.

كل مستخدم يستطيع إرسال Ranking واحد فقط لكل Event.

بعد انتهاء Event: يحسب النظام Aggregate Ranking.

النتيجة تظهر ترتيبًا نهائيًا مبنيًا على مشاركات المستخدمين.

23. PREDICTION
Creator يطرح Prediction.

مثال عام:

من سيفوز؟

المستخدم يختار Prediction.

Creator يستطيع لاحقًا Resolve النتيجة.

لكن:

لا يستطيع Creator تغيير Result بعد Resolve.

عند Resolve:

OPEN
→ RESOLVED
→ LOCKED
المستخدمون الذين شاركوا يحصلون على Result Notification.

24. QUIZ
Quiz هو Event له إجابة صحيحة.

Creator ينشئ عدة Questions.

كل Question يحتوي على:

Question
Optional Image
Answers
Exactly one correct answer
يحدد Creator عدد الأسئلة ضمن حد معقول.

كل سؤال له Timer.

الإجابة الصحيحة تعطي Score.

الإجابة الخاطئة = 0.

بعد انتهاء Quiz:

Final Score
Ranking
Correct Answers
يتم حفظ النتيجة.

لا يمكن تعديل Questions بعد بدء Quiz.

25. IMAGE COMPARISON
Creator يرفع صور المقارنة.

يجب أن يكون هناك عدد محدد ومعقول من الصور.

كل Image:

Image
Optional title
Optional description
المستخدم يختار صورة واحدة.

بعد النهاية:

Votes
Percentages
Winner
لا تكشف هوية المصوتين للعامة.

Creator يستطيع رؤية التفاصيل.

26. CHALLENGE
Challenge هو Event يدعو المستخدمين لتنفيذ مهمة.

يحتوي:

Challenge Title
Description
Rules
Deadline
Optional reference image
المشاركة تكون عبر Submission.

Submission يمكن أن يحتوي:

Text
Image
لا تجعل Challenge يعتمد على Game Engine.

بعد انتهاء Challenge:

تبقى Submissions في Archive.

إذا لم توجد آلية حكم آلية محددة: لا تخترع AI Judge.

Creator هو صاحب قرار Winner/Result.

بعد تثبيت النتيجة لا يمكن تغييرها.

27. OPEN DISCUSSION
Open Discussion:

Topic
Description
Optional Image
المستخدمون يناقشون.

لا توجد إجابة صحيحة.

لا يوجد Winner.

لا يوجد Score.

يمكن:

Comment
Like/React
Share
بعد النهاية: يصبح Discussion Archive.

28. Multi-Group Events
عند إنشاء Multi-Group Event:

Creator يحدد مجموعة أو أكثر.

يجب أن يكون Creator عضوًا في كل Group المستهدفة.

Event واحد = Event واحد.

لا تنشئ نسخة منفصلة لكل Group.

لكن Visibility تكون حسب Group membership.

إذا خرج Creator من إحدى المجموعات لاحقًا:

لا تحذف Event تلقائيًا.

إذا كانت هناك صلاحية لإدارة Event، تبقى صلاحيات الإدارة حسب قواعد النظام.

29. Global Events
Global Event يظهر في مساحة Events العامة.

ويمكن أن يظهر في Home.

ولا يحتاج موافقة مجموعة.

Global Event ليس Game.

Global Event يمكن مشاركته عبر Social Layer.

30. Group Event من Chat
عند إنشاء Event من Group Chat:

ينشر System Card في Chat.

مثلاً:

Event Created
[Title]
[Participate]

بعد انتهاء Event:

يتم حذف الـActive Event Card من العرض الحي في Chat.

ثم ينتقل إلى Chat Archive.

احتفظ بكل البيانات في Archive.

لا تحذف البيانات من قاعدة البيانات لمجرد اختفاء الرسالة النشطة.

35. Creator Permissions
Creator يستطيع:

End Event
Delete Event
View Participants

تغيير Locked Result
التلاعب بـScore
بعد انتهاء Event، النتيجة تصبح immutable.

36. Event Management Permissions
استخدم نظام صلاحيات المجموعة الموجود في Pubget.

الصلاحيات يجب أن تعتمد على:

Manage Events
والمستخدم الذي يملك هذه الصلاحية يستطيع إدارة Group Events ضمن نطاق مجموعته.

لكن Creator يبقى صاحب Event.

لا تجعل Member يستطيع حذف Event لشخص آخر لمجرد أنه عضو.

37. Notifications
أنشئ Notifications فقط للأحداث المهمة:

Event invitation/relevant publication
Event ending soon عند الحاجة
Event ended for participants
Event result available
Comment/reaction where appropriate
Creator resolution
لا ترسل Notification لكل View.

لا ترسل Notification لكل insignificant interaction.

38. Event Search
Search يجب أن يستطيع العثور على:

Event title
Creator
Relevant content
مع احترام Visibility.

لا يمكن لمستخدم رؤية Private Group Event فقط لأنه بحث عنه.

Creation limit

40. Race Conditions
خصوصًا:

Vote
Multiple choice
Ranking submission
Quiz answer
Prediction
Event ending
Creator resolution
كلها يجب أن تكون idempotent.

إذا ضغط المستخدم Submit مرتين:

يتم احتساب المشاركة مرة واحدة.

إذا انتهى Event أثناء Submit:

يجب أن يقرر Server أي عملية لها الأولوية وفق timestamp/server state.

لا تترك حالة نصف مكتملة.

41. Event Ending
عند EndAt:

Server ينقل Event إلى ENDED.

بعدها:

أغلق participation
احسب result
Lock result
حفظ Archive
إرسال notifications
تحديث Discovery
لا تعتمد على أن هاتف المستخدم كان مفتوحًا عند انتهاء Event.

47. Final Acceptance Criteria
لا تعتبر Events مكتملة حتى:

يمكن إنشاء Event من Group Chat.
يمكن إنشاء Event من Home +.
Daily limit = 2.
Global Events تعمل.
Multi-Group Events تعمل.
Group Events تعمل.
كل الـ12 Event Types موجودة.
كل Type له UI/logic مناسب.
Participation لا تتكرر.
Results لا تتلاعب.
Events تنتهي تلقائيًا.
Archive يعمل.
Creator Analytics تعمل.
Participant Result Notification تعمل للأنواع المناسبة.
Home يعرض 3 Events فقط.
View More يفتح Discovery.
Top shortcut يفتح نفس Discovery.
Profile يعرض My Events.
Search يحترم Visibility.
Chat Event Card يعمل.
Chat Archive يعمل.
Permissions تعمل.
Security Server-side.
Pagination تعمل.
لا توجد infinite listeners.
لا توجد orphaned Events.
لا توجد impossible states.
لا يوجد أي اعتماد معماري على Games.
نفذ النظام كاملًا، اختبر كل Type وكل Scope، وأصلح جميع أخطاء runtime/build/security قبل إنهاء المهمة.
