# PUBGET — FULL SECURITY HARDENING + APPLICATION INTEGRITY AUDIT + INCIDENT RECOVERY + REGRESSION TESTING

You are working on the Pubget Flutter/Firebase application.

This is a production-oriented security and integrity task.

IMPORTANT:
This task has TWO major objectives:

OBJECTIVE A:
Perform a comprehensive professional security audit and hardening of the entire application and Firebase backend.

OBJECTIVE B:
Investigate, identify, and safely repair the damage and corrupted/abnormal data caused by a suspected unauthorized user who appears to have exploited weak Firebase/Firestore authorization and manipulated application data.

The application must remain normally usable after hardening.

Do NOT solve security by simply disabling features or making the application unusable.

The intended final state is:

NORMAL USERS:
Can use Pubget normally and freely perform every legitimate action that the existing application is designed to allow.

UNAUTHORIZED USERS / ATTACKERS:
Cannot bypass the application and directly manipulate protected Firebase data, escalate privileges, impersonate users, access private data, manipulate economy/premium/admin fields, modify other users' data, or access resources they do not own or have permission to access.

==================================================

Before modifying production data or production security configuration:

2. Understand the current architecture.
3. Identify all Firebase resources.
4. Identify all Firestore collections and subcollections used by the application.

DO NOT assume every abnormal document was created by the suspected attacker.

DO NOT delete users, groups, messages, requests, or other data merely because they look unusual.

DO NOT destroy evidence before determining what happened.

DO NOT deploy a blanket deny-all rule to production if it breaks legitimate application functionality.

DO NOT use:

allow read, write: if true;

as a global fallback.

- generate an incident report;
- identify candidate corrupted documents;
- explain why each candidate is considered corrupted;
- prefer reversible or auditable changes;
- never silently delete legitimate user data.

Clearly report what cannot be completed because of missing access.

4. FIRESTORE SECURITY RULES
==================================================

Create or completely redesign firestore.rules if necessary.

The rules must follow:

DEFAULT DENY.

Unknown collections must NOT automatically become writable by authenticated users.

Never use a global fallback that gives authenticated users unrestricted access.

For every collection define explicit permissions.

IMPORTANT PRODUCT REQUIREMENT:

Security must NOT destroy normal Pubget functionality.

A normal authenticated user must be able to perform every legitimate action that the existing Pubget product intentionally allows.

Security must prevent bypassing the application logic, not prevent the legitimate feature itself.

For every write operation determine:

- Is the user authenticated?
- Is the user the owner?
- Is the user a legitimate participant?
- Is the user a member of the group?
- Is the user a moderator?
- Is the user an administrator?
- Which exact fields are allowed to change?
- Which fields must never be controlled by the client?
- Does the new data preserve ownership?
- Does the new data preserve identity?
- Does the new data preserve role?
- Does the new data preserve server-controlled state?

Use field-level restrictions wherever appropriate.

Examples:

A user should be able to update legitimate profile fields.

But the user must not be able to change:

isAdmin
isBanned
coinsBalance
subscription state
privileged roles
server-only reward fields
security state
other users' identities

unless there is an explicitly authorized backend mechanism.

For groups:

Normal users should retain legitimate group functionality.

But users must not be able to:

- change another group's owner
- make themselves founder/admin
- modify another group's members without permission
- bypass membership requirements
- manipulate protected group state
- delete groups they do not control

For messages:

Users may send legitimate messages.

But sender identity must come from request.auth.uid, not from arbitrary client-controlled data.

Users must not be able to impersonate another sender.

For private chats:

Only legitimate participants should be able to access private chat data.

For Mafia:

Players should be able to participate normally.

However:

- private roles must not be exposed to other players
- clients must not decide winners
- clients must not arbitrarily change roles
- clients must not manipulate rewards
- clients must not manipulate protected game state

If server-side authority is required, move the operation to Cloud Functions or another trusted backend mechanism.
