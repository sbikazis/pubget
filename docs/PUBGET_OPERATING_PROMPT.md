## البند 1 — بروتوكول الوثيقة (أهم قاعدة في هذا الملف)

1. الوثيقة المرجعية (PUBGET_MASTER_SPEC.md) هي الحقيقة الوحيدة. عند كل أمر من المالك ("نفّذ المحور X"، "تحقق من النظام Y"، "أصلح Z")، أول فعلة: ارجع للوثيقة واقرأ المحور كاملاً قبل لمس أي ملف.
2. أي تعارض بين الوثيقة وأي كود قديم أو وصف سابق أو اجتهاد شخصي ← تفوز الوثيقة.
3. نقطة غير مغطاة ← طبّق "قواعد الحكم" (الملحق أ في الوثيقة) ووثّق قرارك في التقرير.
4. ممنوع أن تسأل المالك عن قرارات محسومة في الوثيقة. ممنوع أن تخترع منتجاً جديداً. ممنوع "تقريباً" — إما حسب المواصفة أو موثّق كقرار مهندسي.
5. لا تعدّل الوثيقة إلا بطلب صريح مكتوب من المالك.

## البند 2 — قانون الجودة المطلق (يُطبق على كل سطر)

- Server هو الحقيقة: الرتب، الصلاحيات، العملات، المكافآت، النتائج، العدادات، حدود الإنشاء — Functions/Transactions/Rules، لا Client.
- Idempotency لكل Action حساس. State Machines لا booleans. لا race conditions. لا duplicate actions.
- ممنوع نهائياً: fake data، placeholder، زر ميت، "coming soon"، onPressed فارغ، TODO مموّه، مشاهدات/إحصاءات مخترعة، محتوى hardcode في المسارات الإنتاجية.
- كل شاشة: Loading/Empty/Error/Offline/Retry كاملة. لا شاشة بيضاء، لا spinner أعمى.
- ممنوع إضافة أي Package جديد دون إدراجه في التقرير مع مبرره. ممنوع حذف حزم قائمة.
- ممنوع كسر نظام يعمل. ممنوع تعديل lib_legacy. ممنوع تغيير أنظمة خارج نطاق مهمتك إلا لنقطة تكامل موثقة.
- الأداء ليس ترفاً: Pagination، Lazy loading، Caching، لا rebuild زائد، dispose سليم، لا listeners مفتوحة.
- العربية/الإنجليزية: تبديل لغة يغيّر التطبيق كله 100% — كلمة واحدة خاطئة = عيب حرج. RTL مُدقَّق.

## البند 3 — قانون GitHub الصارم (الذي تعثّر فيه سابقاً — يُطبق حرفياً)

1. كل مهمة = فرع مستقل من آخر `main` نظيف: `feature/<رقم-المحور>-<وصف-انجليزي-قصير>` (مثال: `feature/15-kirari-audio-system`).
2. لا تدفع شيئاً إلى main أبداً. لا تدمج أبداً. المالك وحده يدمج.
3. بوابة ما قبل فتح الـPR (إلزامية وغير قابلة للتفاوض):
   - `flutter analyze` → صفر issues.
   - `flutter test` → كل الاختبارات ناجحة (أو مرفق تفسير لأي إزالة).
   - إن لُمست Firestore Rules أو Storage Rules → اختبارات Emulator للقواعد ناجحة ومذكورة في التقرير.
   - `flutter build apk --debug` (أو الوحدة المناسبة) → ناجح.
   - مراجعة diff كاملة بعينك: لا ملف مشوه، لا تنسيق مكسور، لا ترجمات محذوفة، لا أسرار/مفاتيح صلبة، لا تضمين عشوائي لملفات خارج النطاق.
4. افتح Pull Request كامل الوصف، وفي نهاية مهمتك أعطِ المالك: رابط الـPR + عنوانه + ملخص التغييرات.
5. commits صغيرة موضوعية (message واضح). ممنوع commit واحد عملاق غامض.
6. إن فشل أي بند من البوابة: أصلح وأعد. إن تعذّر إصلاح تقني أمني دون إضعاف: توقف واكتب "BLOCKED" مع السبب — لا تكسر الأمان لتكمل.
7. بعد أي دمج من المالك، المهمة التالية تبدأ بمزاممة main الجديد.

## البند 5 — كيف يعطيك المالك الأوامر (أمثلة صالحة)

- "نفّذ المحور 15" ← تنفذ نظام Kirari كاملاً حسب الوثيقة.
- "نفّذ 15.4 فقط" ← نظام الصوت فقط.
- "تحقق من المحور 20" ← تدقيق سلامة محرك الإنجازات دون تغيير إلا لإصلاح خلل مثبت.
- "طوّر الواجهة في المحور 09 مع بقاء المنطق" ← تعديل UI فقط.
- "أصلح أزرار الملف الشخصي (18.1)" ← إصلاح محدد موثق.
- "راجع الأمان للمحاور 12-13" ← تدقيق أمني + تقرير، دون تغييرات إلا بـPR منفصل.
- أي أمر غامض ← طلب توضيح محدود، أو افتراض معقول موثق في التقرير.

## البند 6 — شروط التوقف الفوري (أبلغ ولا تخمن)

توقف واكتب BLOCKED عند: تضارض داخل الوثيقة نفسها · هجرة بيانات مدمرة مطلوبة · إضعاف أمن لا مفر منه · اعتماد خارجي غير متاح (مفتاح API، باقة Blaze...) · قرار منتجي غير موجود في الوثيقة إطلاقاً.
ما عدا ذلك: استخدم حكمك الهندسي وتابع ووثّق.
