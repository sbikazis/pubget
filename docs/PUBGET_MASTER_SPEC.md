## المحور 00 — التعريف والهوية والمبادئ الذهبية

### 0.1 ما هو Pubget
Pubget ليس تطبيق أنمي، ولا دردشة، ولا منصة فيديو. Pubget هو:

> فضاء اجتماعي (Anime Social Universe) يجمع الأشخاص والمجموعات والدردشات والألعاب والأحداث والإبداعات والأنمي والاهتمامات في عالم شخصي يبنيه كل مستخدم داخل التطبيق.

الشعار: «عالمك… مجموعتك… مغامرات»

### 0.2 الحلقة الأساسية (Core Loop)
اكتشف ← انضم ← تفاعل ← العب ← أنشئ ← ابنِ هويتك ← اكسب سمعة ← عُد ← اكتشف من جديد.
كل ميزة تُبنى يجب أن تقوّي هذه الحلقة، وإلا تُرفض.

### 0.3 الجودة (تعريف إلزامي)
- بصرياً: فخم، متناسق، أنمي-ياباني الطابع دون مبالغة، داكن/فاتح متقنان، لا طفولية، لا فوضى ألوان.
- تقنياً: استجابة فورية، لا إعادة بناء زائدة، Pagination في كل قائمة، Lazy loading، Caching، معالجة أخطاء حقيقية، حالات Offline، منع التكرار و race conditions.
- اجتماعياً: اكتشاف سهل، تشجيع المشاركة والعودة اليومية، لا دفن للمجموعات الصغيرة ولا للمستخدم الجديد.
- وظيفياً: كل زر يعمل، كل شاشة لهدف، لا أزرار ميتة، لا placeholders، لا fake data، لا "قريباً".

### 0.4 قواعد حديدية (تُطبق في كل محور دون استثناء)
1. **Server هو الحقيقة**: الرتب، الصلاحيات، العملات، المكافآت، النتائج، العدادات الحساسة، حدود الإنشاء — كلها تُتحقق Server-side (Functions/Rules) وليس في الـ Client أبداً.
2. **Idempotency**: كل Action حساس له معرّف فريد؛ الضغط المزدوج/إعادة الإرسال/إعادة الاتصال لا تُضاعف التأثير أبداً.
3. **State Machines**: لا boolean فوضوي؛ كل كيان له حالات وانتقالات صريحة؛ الانتقال غير القانوني ممنوع.
4. **لا بيانات وهمية**: لا views مزيفة، لا trending مقصود، لا analytics مخترعة. إذا تعذّر metric تقنياً تُخفى الواجهة بدل اختراعه.
5. **العزل المعماري**: الأنظمة تتكامل عبر interfaces واضحة؛ Chat لا يملك منطق الألعاب؛ Events لا يستورد Game Engine؛ Reels Domain مستقل.
6. **لا تكسر ما يعمل**: أي نظام يعمل صح يُحافظ عليه (أو يُطوّر بحذر)؛ ما يتعارض مع هذه الوثيقة يُستبدل عمداً وبوثيقة.
7. **lib_legacy**: مرجع فقط — ممنوع التعديل عليه، يُستأنس به للأفكار والأصول.

### 0.5 ما تم إلغاؤه نهائياً (ممنوع إحياؤه)
- إيقاف الإعلانات مقابل عملات (تُعوَّض المنشآت سابقاً عملات + عنصر نادر + إشعار).
- المنتجات الفيزيائية في المتجر.
- أي Event Type خارج الـ12 المعتمدة، وأي لعبة خارج الأربع المعتمدة.
- أي نظام رتب قديم — النظام الوحيد المعتمد هو مصفوفة المحور 09.

## المحور 01 — المعمارية التقنية

### 1.1 الستاك
- Flutter (Dart null-safety) + Firebase (Auth, Firestore, Storage, Functions, FCM) + Provider لإدارة الحالة (مع إعادة تنظيم كاملة حول Domains).
- الطبقات الإلزامية: UI ← Provider/Controller ← Repository/Service ← Firebase/Media Provider. ممنوع وضع Business Logic داخل Widgets، وممنوع على UI الوصول المباشر لـ Firestore إلا عبر Repositories.

### 1.2 الهيكل
lib/app (routing, di) · lib/core (theme, constants, utils, errors, result) · lib/features/ (كل Domain: models, providers, services, screens, widgets) · lib/widgets مشتركة. كل Domain مسؤولية واحدة واضحة، بلا God classes، بلا dependencies دائرية.

### 1.3 Design System (يُبنى أولاً قبل أي شاشة)
- الألوان: Royal Purple أساسي + Gold مميز + أسطح داكنة فاخرة + وضع فاتح مصمم عمداً (ليس انعكاساً آلياً). نجاح/تحذير/خطأ/معلومة + حالات تفاعل (pressed/disabled/loading).
- الطابع: بنفسجي ملكي وذهب بذكاء وبدون إغراق؛ لمسة يابانية خفيفة (خطوط/زخارف/مصطلحات الرتب)؛ فخامة حتى بدون صور.
- Typography: display/headline/title/body/label/caption + أرقام مميزة؛ يدعم العربية والإنجليزية والـ RTL حقيقياً.
- Spacing/Shape/Elevation: مقاييس مترابطة، أنصاف أقطار موحدة، ظلال متحفظة.
- Motion: مدد و easing موحدة؛ حركة للتغذية الراجعة والهرمية فقط؛ لا حركات ثقيلة.
- مكونات مركزية إلزامية: AppBars، أزرار، بطاقات، Media Cards، Avatars، Badges، Chips، Tabs، BottomSheets، Dialogs، Snackbars، Skeletons، Empty/Error states، Counters، Comment/Reaction، بطاقات (مجموعة/مستخدم/لعبة/حدث/ريل/عمل). ممنوع على أي Feature اختراع لغته البصرية الخاصة.

### 1.4 التعريب
- لغتان فقط: العربية (افتراضية) والإنجليزية. تُختار في تسجيل الدخول وتُغيَّر من الإعدادات.
- التبديل يغيّر التطبيق كله 100% — كلمة إنجليزية واحدة في الواجهة العربية (أو العكس) تعتبر عيباً حرجاً.
- كل النصوص عبر نظام Localization مركزي — ممنوع أي نص hardcode داخل المنطق.
- RTL يُدقّق في: الأسهم، الأيقونات الاتجاهية، المحاذاة، التمرير، الأرقام والتواريخ، BottomSheets، التمرير بالسحب.

## المحور 02 — قواعد عابرة لكل النظام

### 2.1 حالات الواجهة الإلزامية
كل شاشة/قائمة تملك: Loading (Skeleton لا Spinner أعمى)، Loaded، Empty (برسالة + فعل تالي ذكي)، Error (مفهوم + Retry)، Offline (بيانات مخزنة متاحة + Retry)، Permission Denied، Expired. ممنوع: شاشة بيضاء، Spinner لا نهائي، UI متجمد، خطأ خام من Firebase يظهر للمستخدم.

### 2.2 Offline / Retry / Idempotency
كل عملية كتابة تُسأل: ماذا لو ضغط مرتين؟ انقطع النت؟ أُغلق التطبيق؟ نجح السيرفر وانتهت مهلة العميل؟ الرسائل الفاشلة تظهر معلّقة مع Retry/Delete ولا تُعلَّم "وصلت" كذباً.

### 2.3 الروابط العميقة (Deep Links)
مسارات معتمدة: `/group/{id}` `/profile/{username}` `/reel/{id}` `/anime/{id}` `/work/{id}` `/event/{id}` `/hashtag/{tag}` `/audio/{id}`.
- التطبيق مثبت ← يفتح المكان مباشرة. غير مسجل ← Login ثم عودة تلقائية للمكان. غير عضو في مجموعة ← Group Details. بلا صلاحية ← شاشة مناسبة واضحة.
- التنفيذ عبر Android App Links + Firebase Hosting rewrites (Firebase Dynamic Links توقفت نهائياً — ممنوع استخدامها). كل رابط يعرض Rich Preview (صورة/عنوان/وصف) حيثما أمكن.

### 2.4 مكافحة الإساءة (Anti-Abuse) — عبر التطبيق
منع: views مزيفة، سبام الإعجاب/التعليق، النشر المتكرر، سبام الإشعارات، الرفع المسيء، التفاعلات الآلية، تلاعب التوصيات. إشارات: unique users، عمر الحساب، جودة التفاعل، الزمن، الأنماط المتكررة، العناقيد المشبوهة. لا يُثقّل على التطبيق.

### 2.5 المحافظة والعملات (Core)
- كل حركة Coins تسجل في Ledger: (transactionId, userId, type, amount, source, timestamp, metadata).
- الصرف والمنح Server-side Transactions فقط؛ العميل لا يستطيع زيادة رصيده بأي طريقة.
- العملات وقود انتشار التطبيق: تُكافأ السلوكيات المفيدة الحقيقية فقط، ولا تُدفع مقابل كل نقرة (ممنوع Click farming).

## المحور 03 — المصادقة والانضمام وهوية المستخدم

### 3.1 طرق الدخول (المغلقة)
Email + Password فقط، و Google فقط. لا فيسبوك، لا أخرى.

### 3.2 الشاشات
- Splash: ليست شاشة انتظار — تُهيئ Firebase، تفحص Auth، تُحمّل أقل User state، تفحص الشبكة والإصدار الأدنى (Force/Soft update)، تجهز الثيم والروابط، وتحدد الوجهة الأولى.
- Login: بريد + كلمة مرور + Google + نسيت كلمة المرور + إنشاء حساب. فخم ومختصر بلا خطوات زائدة.
- Register: بريد + كلمة مرور + تأكيد + Google + الشروط (القبول إلزامي) + التحقق قبل الإنشاء قدر الإمكان.
- شاشة إكمال المعلومات (تظهر مباشرة بعد أول إنشاء حساب):
  - إلزامي: الاسم (حر) + اللقب/اسم المستخدم (Username — يجب أن يكون فريداً على مستوى التطبيق ويُتحقق منه Server-side مع فحص فوري أثناء الكتابة) + صورة البروفايل.
  - اختياري (يترك كلياً بلا أي إجبار): صورة الغلاف، العمر، الجنس، الدولة، المفضلة من الأنمي (عبر نظام Anime Hub بالبحث لا بالكتابة الحرة)، البايو، روابط التواصل الاجتماعي.

### 3.3 Onboarding — أول 10 دقائق
ليست شروحات تعليمية؛ المستخدم يعيش التطبيق: مجموعة نشطة ← إيديتات قوية تبهره ← فعالية/لعبة ← اهتمام أنمي ← أول علاقة اجتماعية. لا شاشات تعليمية متتالية؛ كل توجيه سياقي داخل التجربة نفسها.

## المحور 04 — الهيكل العام للتنقل (الأشرطة والقوائم)

### 4.1 الشريط العلوي (إعادة تنظيم إلزامية — المواضع تبقى، الجودة ترتفع)
الفوضى الحالية في ترتيب الأزرار تُلغى. الترتيب المعتمد (RTL):
`[أيقونة/شعار التطبيق]` ← `عداد العملات (+)` ← `زر متجر التنين` ← `البحث` ← `الإشعارات + دائرة حمراء بعداد` ← `صورة البروفايل` ← `زر القائمة الجانبية (☰)`.
- نفس الأزرار ومواضعها العامة، لكن بجودة عرض أعلى: عداد عملات حي متزامن، أيقونات موحدة، حالات تفاعل واضحة.

### 4.2 الشريط السفلي (يُحافظ على توزيعه الحالي كما هو)
`اكتشف (الرئيسية)` · `مجموعاتي` · `منضم لها` · `الخاص` · `إيديتات`.
- كل تبويب بعداد دائرة حمراء مستقل (من محرك Unread المركزي).
- "اكتشف" هو الصفحة الرئيسية (Home).

### 4.3 قائمة الإنشاء (+)
خيارات مغلقة: مجموعة · ريلز · حدث · عمل إنتاجي. لا غير.

### 4.4 القائمة الجانبية (☰)
تحسين الواجهة مع الإبقاء على البنية: حسابي، الدردشات الخاصة، مجموعاتي، المجموعات المقترحة، Anime Hub، الإيديتات، الأعمال الخاصة، الأحداث، متجر التنين، Premium، الإعدادات، الدليل، تسجيل الخروج (في الأسفل دائماً).

### 4.5 قاعدة النقر الواحد
أي فضاء رئيسي يُبلغ بأقل عدد ممكن من الضغطات؛ ممنوع Menu←Submenu←Submenu←Page إذا أمكن الوصول المباشر. Home هي نقطة الربط لكل الفضاءات (من ريل ← صانع ← أنمي ← مجموعة ← حدث ← مستخدمون...).

## المحور 05 — الصفحة الرئيسية (Home / اكتشف)

### 5.1 التعريف
Dynamic Discovery Surface — لوحة فنية حية، ليست Feed جامد. تجيب: "ماذا أفعل الآن؟"

### 5.2 الترتيب الإلزامي
1. أعلى الشاشة دائماً وبشكل مثبّت: المجموعات المروّجة (Promoted Groups) — مروّجة = لجميع المستخدمين بنفس الشكل.
2. ثانياً: الفيديوهات/الإيديتات حسب اهتمام المستخدم (شخصية لكل مستخدم).
3. ثم: باقي الأقسام بترتيب يتبدل ذكياً بين الزيارات (Randomized order بعد الثابتين أعلاه) — كل قسم يظهر بتصميم فخم مستقل حسب طبيعته.

### 5.3 الأقسام (تغطي كل ما يمكن نشره في التطبيق)
المجموعات المروّجة · إيديتات مخصصة · الأحداث (3 فقط + عرض المزيد) · أعمال المستخدمين الخاصة · أشخاص مقترحون · مجموعات مقترحة · مجموعات صاعدة (Rising) · أنميات الموسم الحالي/قيد الإنتاج · أنمي الأسبوع · شخصيات شعبية · نشاط الأصدقاء · صنّاع صاعدون · إنجازات/تقدم · محتوى جديد حسب آخر نشاط.
- كل قسم يملك تصميماً خاصاً به (Grid/ hero rail / بطاقات) — لا بطاقة واحدة مع تغيير العنوان فقط.
- زر "عرض المزيد" في كل قسم ← صفحة قسم مستقلة، وكلها متاحة أيضاً من القائمة الجانبية.

### 5.4 التخصيص والترتيب
- الترتيب يتغير حسب: الاهتمامات، النشاط، الزمن، جودة المحتوى، الحداثة، المتابعات، مجموعات المستخدم. ممنوع إلغاء نوع محتوى نهائياً بسبب خفوت الاهتمام — تخفُض الأولوية فقط ويبقى قابلاً للاكتشاف.
- أولوية الترتيب العام: المجموعات المروّجة ← الإيديتات ← الأحداث ← باقي الاكتشاف.
- ممنوع إظهار سبب توصية زائف (لا "لأنك تتابع" بلا بيانات حقيقية).

### 5.5 الأداء
Infinite scroll + Pagination + Lazy loading + Section-level loading + Skeletons + Prefetch خلفي. لا تحميل كلي، لا listeners مفتوحة.

## المحور 06 — البحث (عالمي وسياقي)

- شاشة بحث رئيسية + بحث سياقي في أي مكان فيه >10 عناصر (الأعضاء، الشخصيات، الأنمي، الملصقات، الوسائط...).
- نص + فلتر نوع الكيان: مجموعة / فيديو(ريلز) / عمل خاص / حدث / مستخدم / أنمي / شخصية / هاشتاغ / صوت.
- نتائج ريلز مرتبة (relevance)؛ دعم العناوين البديلة والإنجليزي/الياباني/العربي (Fuzzy)؛ Ranking: تطابق دقيق ← صلة ← شعبية ← حداثة ← علاقة المستخدم ← السياق.
- سجل بحث حديث، Empty states، Pagination، Deep links من النتائج.

## المحور 07 — المجموعات

### 7.1 الأنواع (المغلقة — الثلاثة تبقى، وكلها يمكن أن تكون Private)
1. عامة (Public Group) 2. تقمص دور مربوطة بأنمي (Anime Roleplay) 3. تقمص دور مفتوح (Open Roleplay). البنية تسمح بأنواع مستقبلية دون إعادة بناء.

### 7.2 الإنشاء (Wizard)
هوية أساسية (اسم/صورة/وصف) ← النوع ← القواعد (عامة/خاصة · موافقة المؤسس · حد الأعضاء · قواعد المحتوى) ← التخصيص (خلفية الدردشة، عناصر الهوية، رسالة ترحيب) ← الصلاحيات ← معاينة ← نشر.
- رسالة ترحيب تلقائية قابلة للتخصيص عند دخول عضو جديد.

### 7.3 الانضمام
- افتراضي: دعوة المؤسس فقط + خيار المؤسس "فتح الانضمام للجميع".
- مجموعة مقيدة: طلب انضمام ← انتظار ← قبول/رفض مع إشعار. قائمة الطلبات لأصحاب الصلاحية.
- Flow تقمص الدور: تفاصيل ← اختيار شخصية (من قاعدة بيانات الشخصيات مع اقتراحات ذكية — المستخدم يختار دائماً، النظام يقترح فقط: بحث/شعبية/متاحة/مستخدمة حديثاً) ← تحقق ← انضمام/طلب ← دردشة.
- توفر الشخصية: إن كانت الشخصية محدودة يمنع التعارض حسب سياسة المجموعة، ويستطيع المؤسس السماح بالتكرار.
- قواعد المجموعة تُعرض قبل الانضمام.

### 7.4 قاعدة الدخول للمجموعة
غير العضو أو المؤسس ← صفحة تفاصيل المجموعة (منظوره). العضو العادي ← يدخل مباشرة للدردشة. المؤسس ← صفحة تفاصيل من منظوره (تُطوَّر بصرياً).

### 7.5 اكتشاف المجموعات الصغيرة (Rising Groups) — نظام إلزامي
- مشكلة "مجموعة جديدة ← لا أعضاء ← لا ظهور ← موت" ممنوعة.
- Rising Groups: مجموعات حديثة تحقق مؤشرات نشاط حقيقية (عمر المجموعة، النشاط، معدل الرد، اكتمال الملف، انتظام النشاط، جودة التفاعل — وليس عدد الأعضاء فقط) تحصل على فرصة ظهور.
- Anti-Manipulation: مؤسس لا يستطيع تصعيد مجموعته بحسابات وهمية — إشارات: unique users، عمر الحساب، جودة التفاعل، الزمن، الأنماط المتكررة.
- مجموعة جديدة تُفعَّل: إعداد الملف ← دعوة أصدقاء ← أول Event ← نشر ← Discovery exposure (مساعد تفعيل داخلي بخطوات).

### 7.6 تفاصيل المجموعة
اسم، صورة، وصف، نوع، الأنمي المرتبط، عدد الأعضاء، النشاط، القواعد، المؤسس، الرتب، سياسة الانضمام، تاريخ الإنشاء، أحداث/نشاط، وسائط المجموعة (صور/فيديو/ملصقات/إيديتات مشتركة مع بحث وفلاتر)، زر مشاركة الرابط.
- قائمة الأعضاء (تُطوَّر بصرياً): Avatar + اسم + الرتبة + شارة الرتبة + حالة الاتصال + شخصية التقمص + مؤشر المؤسس + علاقة معجب/صديق عند الحاجة. الضغط على أي مستخدم ← ملفه الشخصي (في كل أنحاء التطبيق).
- أفعال خطرة تتطلب تأكيداً مزدوجاً: تفكيك المجموعة، نقل الملكية، إزالة Shogun، تغييرات صلاحيات كبرى. المؤسس لا "يغادر" كعضو عادي — يجب نقل ملكية أو تفكيك. تفكيك = تأكيد + شرح + تأكيد نهائي + Server-side + إشعار للأعضاء.

### 7.7 زر القائمة (☰) داخل المجموعة
إضافة أعضاء (من الدردشات الخاصة/الأصدقاء ← رسالة ترحيب فخمة بكل معلومات المجموعة + الرابط) · نسخ رابط المجموعة · معلومات المجموعة · وسائط المجموعة · قائمة الأعضاء · تعديل المجموعة (للصلاحية فقط) · خلفية الدردشة · مغادرة المجموعة · تفكيك المجموعة (Mikado فقط).

## المحور 09 — دردشة المجموعة (نموذج WhatsApp المطوَّر بهوية Pubget)

### 9.1 الشريط العلوي
رجوع ← صورة المجموعة + الاسم (إن طال الاسم يعمل Marquee/تمرير سكّي) ← قائمة (☰).

### 9.2 الخلفية
- افتراضياً عند أول دخول: خلفية Pubget الافتراضية. تغييرها من ☰ ← تعديل المجموعة (صلاحية manageBackground).
- نظام تباين تلقائي إلزامي: يحسب تلقائياً تباين الفقاعات والنص والحدود والظل والـ Overlay حسب أي خلفية — الرسائل مقروءة دائماً مهما كانت الخلفية.

### 9.3 الفقاعات
موزعة ومرتبة ومريحة، حجم معقول (نموذج WhatsApp). ترويسة الرسالة: Avatar + اسم المرسل بلون رتبته + شارة الرتبة + اسم شخصية التقمص إن وجد + الوقت + حالة القراءة.

### 9.4 حالة القراءة (موحدة للنصوص والصوتيات وكل الوسائط)
🔴 حمراء = لم تصل · 🟡 صفراء = وصلت ولم تقرأ · 🟢 خضراء = قُرئت.

### 9.5 أنواع الرسائل وطريقة عرضها (نموذج WhatsApp)
- ملصق: بلا إطار — الصورة فقط + الاسم فوق + الوقت أسفل.
- صورة/فيديو: إطار خفيف جداً + الاسم فوق + الوقت أسفل ← الضغط يفتح عارضاً ملء الشاشة (سحب/تكبير/تشغيل/حفظ/مشاركة حسب الصلاحية).
- ريلز/محتوى مشترك: بطاقة غنية (غلاف + صانع + وصف مختصر + زر فتح) — مرجع لا نسخة مكررة.
- صوتي/تسجيل: مشغل فقاعي بمواصفات WhatsApp.
- رسائل نظامية (انضمام/رتبة/لعبة/حدث): فخمة ومختصرة، لا تغرق الدردشة.
- أفعال الرسالة (حسب النوع والصلاحية): رد، نسخ، حذف، تثبيت، مشاركة/إعادة توجيه، تفاعل React، إبلاغ، حفظ، تعديل (نصوصي فقط).

### 9.6 شريط الإدخال السفلي
نص + Emoji + ملصقات (نظام الملصقات الموجود: محفوظة/مُنشأة/مجموعات — سريع ومخزّن) + GIF + وسائط + تسجيل صوتي + زر الفعاليات والألعاب.
- التفاعل بالملصقات والإيموجي والألوان بجودة فخمة في كل أنحاء الدردشة — ممتلئة ومرتبة دائماً.

### 9.7 Unread Engine مركزي
يحسب: غير المقروء لكل مجموعة/خاص/إشعارات/منشن/حدث. يغذي الدوائر الحمراء في كل مكان. يمنع: قراءة خاطئة، عداد لا ينقص، عداد يرتد، duplicate reads. تحديث آمن.

### 9.8 الأداء
لا إعادة بناء كل الرسائل عند رسالة جديدة (Stable keys، Incremental updates، Cache للوسائط، Pagination للصعود). لا listeners عشوائية على collections كاملة.

### 10.3 قائمة المحادثات الخاصة
Avatar + اسم + آخر رسالة + وقت + عداد غير مقروء. تبويب "الخاص" في الشريط السفلي يحمل دائرته الحمراء.

## المحور 12 — الألعاب (المركز + الألعاب الثلاث)

### 12.1 القواعد الحاكمة
- إنشاء الألعاب من داخل دردشة المجموعة فقط (زر الفعاليات والألعاب ← Game Center). لا من Home ولا من +.
- حد الإنشاء: لعبتان جديدتان/يوم/مستخدم (المشاركة في ألعاب الغير لا تُحسب) — تحقق Server-side مع منع race conditions؛ عند بلوغ الحد: منع + شرح واضح.
- Game Center (يُحافظ على أزراره وأقسامه الحالية، يُطوَّر بصرياً ومنطقياً): Available Games (الأربع دائماً — لا تعطيل) · Active · Waiting · Recent · History · Rules · معلومات كل لعبة (عدد اللاعبين، المدة، الصعوبة، طريقة الفوز، النوع).
- Pipeline إلزامي: زر ← Game Center ← إنشاء ← إعلان في الدردشة ← غرفة انتظار ← اكتمال العدد ← غرفة لعب خاصة خارج الدردشة ← المحرك يرسل أحداثه للدردشة ← نتيجة ← مكافأة ← رسالة نتيجة ← أرشيف.
- غرفة الانتظار: عنوان، قواعد، اللاعبون، العدد/المطلوب، الحالة، شروط البدء، إلغاء. العودة للدردشة مسموحة قبل البدء فقط؛ بعد البدء لا عودة أثناء اللعب. مهلات انتظار لكل لعبة — عند انتهائها: إلغاء + حذف الإعلان النشط + لا مكافآت + لا أيتام (لا Waiting/Requests معلقة أبداً).
- State Machine: CREATED → WAITING → STARTING → IN_PROGRESS → COMPLETED / CANCELLED. الانتقالات غير القانونية ممنوعة.
- فصل تام عن Events: لا دمج ولا abstraction مشتركة؛ الدردشة تستقبل رسائل نظامية فقط ولا تملك منطق اللعبة.
- المكافآت (Server-side، idempotent — مرة واحدة أبداً): خسارة = 2 · تعادل = 5 · فوز = 7–10 حسب الصعوبة.
- انقطاع/إغلاق التطبيق ≠ انسحاب: الحالة محفوظة Server-side، العودة تستعيد المكان دون إعادة تشغيل أو إعادة توزيع.

### 12.2 Guess Character (1 ضد 1)
- كل لاعب يختار شخصية سرية للخصم من قاعدة بيانات الشخصيات (Character ID فعلي، لا اسم حر)؛ مؤقت اختيار — التأخر = خسارة.
- بالدور: سؤال (نعم/لا بأزرار واضحة — لا NLP لتحويل الحالة) أو تخمين (Picker/بحث شخصيات). التخمين الصحيح = فوز؛ الخاطئ = إعلان الخطأ وتبديل الدور.
- مؤقت لكل سؤال؛ مؤقت عام 10 دقائق — انتهاؤه دون فائز = تعادل (5 لكل لاعب). الانسحاب = خسارة مباشرة.

### 12.3 Anime Chain (1 ضد 1)
- سلسلة أدوار: لاعب يقدم أنمي صالحاً من القاعدة مرتبطاً بقاعدة السلسلة المحددة من إجابة السابق؛ تحقق Server-side (موجود، غير مستخدم سابقاً، يحقق قاعدة السلسلة، الدور صحيح، اللعبة جارية، المهلة لم تنتهِ).
- مؤقت لكل دور؛ الفشل/المهلة = خسارة الدور أو الفوز المباشر للخصم عند تحقق الشرط. واجهة مستقلة بصرياً: السلسلة الحالية، اللاعب الحالي، المؤقت، المستخدم، الإدخال/البحث، الإرسال، القواعد.

### 12.4 Emoji Anime Guess (2–4 لاعبين)
- الدور لمالكه ← النظام يختار أنمي ← يقدم 3–4 إيموجي فقط بلا كلام ولا اسم ولا تسريب مباشر ← الباقون يخمنون (بحث في قاعدة الأنمي مع العناوين البديلة) ← الصحيح = نقطة ← انتقال الدور.
- مؤقت للجولة؛ بلا إجابة = جولة بلا نقاط وانتقال. لوحة نقاط حية؛ الأعلى فائز والتعادل تعادل. عدالة الأدوار مضمونة ضد race conditions والانقطاع.
- صعوبة واضحة ومؤقت وترتيب نقاط وscoreboard حي.

### 12.5 الأرشيف والنتائج
كل لعبة منتهية تنتقل للأرشيف (اللاعبون، النتيجة، المدة، المكافأة) بعرض أنيق — ليس قائمة قاعدة بيانات خام. النتيجة لا تتغير أبداً بعد الإتمام.

## المحور 13 — MAFIA (Domain مستقل كامل)

### 13.1 الفلسفة
Social Deduction Game كاملة بدون مشرف بشري: أدوار سرية، فرق، معلومات خاصة، أفعال ليلية، نقاش نهاري، تصويت، إقصاء، شروط فوز، State Machine بسلطة سيرفر كاملة. ليست Event ولا تعتمد عليه.

### 13.2 الإنشاء والاعبون
- من Game Center فقط؛ الحد الأدنى لإنشائها SAMURAI (من مصفوفة المحور 08) — تحقق Server-side لا يمكن تجاوزه.
- العدد: 7–15 لاعباً؛ لا بدء قبل الحد الأدنى؛ بعد البدء Join ممنوع نهائياً.
- Waiting Room + بطاقة إعلان في الدردشة (المنشئ، العدد/النطاق، انضمام، الحالة، القواعد).

### 13.3 الأدوار (المغلقة — لا أدوار أخرى)
Mafia (الفريق الشرير) · Don (قائد المافيا: يشارك في القتل + تحقق خاص "هل هذا Detective؟") · Detective (يفحص لاعباً ليلياً ← النتيجة Mafia / Not Mafia فقط، لا الدور الخام) · Doctor (يحمي لاعباً ليلياً، يجوز حماية نفسه، ولا يحمي نفس اللاعب ليلتين متتاليتين) · Citizen (بلا قدرة ليلية).
- توزيع deterministic حسب العدد، Server-side، بدون إعادة توزيع بعد البدء. سجل الأدوار القديم (silencer/good_boy/spiner...) يُلغى — يبقى Role Registry يسهّل إضافة أدوار مستقبلاً دون تغيير المحرك.

### 13.4 الخصوصية
كل لاعب يرى دوره فقط؛ أعضاء المافيا يعرفون بعضهم؛ المدينة لا تعرف المافيا؛ لا يمكن لأحد قراءة أدوار الآخرين من Firestore (Private Player State محمي بـ Rules + Server Authorization). قناة مافيا خاصة داخل غرفة اللعب (ليست دردشة عامة جديدة).

### 13.5 شروط الفوز (تُفحص بعد كل تغيير في الأحياء — فوراً دون انتظار طور)
- مافيا تفوز عندما يصبح أحياؤها ≥ باقي الأحياء.
- المدينة تفوز عند إقصاء كل المافيا.

### 13.6 State Machine
`WAITING → STARTING → ROLE_REVEAL → NIGHT → DAY → DISCUSSION → VOTING → VOTE_RESULT → RESOLUTION → GAME_OVER` (+ CANCELLED). لا قفزات غير منطقية.

### 13.7 الجولة
- Night (مؤقت Server-side يُعرض فقط): مافيا تختار هدفاً (القرار النهائي يحسبه السيرفر من اختياراتهم) · Doctor حماية · Detective تحقيق · Don قدرته · Citizen لا شيء.
- Night Resolution (deterministic): تحقق ← حل الهدف ← الحماية ← التحقيق ← قدرة Don ← الوفاة ← كتابة النتيجة ← فحص الفوز ← انتقال للنهار. لا تُعرض تفاصيل فردية للآخرين.
- Day: إن قُتل لاعب ← إعلان عام + إقصاء (يفقد التصويت والقدرات والنقاش). بلا قتيل ← إعلان ليلة بلا وفاة.
- Discussion: دور لكل حي بترتيب تحدث ومؤقت (تحدث/إنهاء الدور)؛ غياب لاعب لا يوقف اللعبة — يُتجاوز.
- Voting: سرّي، لا تصويت للنفس (حسب القاعدة المعتمدة)؛ الأعلى أصواتاً يُقصى. تعادل ← إعادة تصويت بين المتعادلين ← استمرار التعادل = لا إقصاء وانتقال لليلة. لا تجميد أبداً.
- Elimination: كشف الدور + كلمات أخيرة قصيرة + انتقال لمشاهد: الميت يشاهد اللعبة لكن لا يرى أي معلومة خاصة لم تكن متاحة له حياً.

### 13.8 الانقطاع والانسحاب
- خلفية التطبيق/إغلاق مؤقت ≠ انسحاب: DISCONNECTED + نافذة عودة؛ العودة تستعيد الدور/الطور/المؤقت دون إعادة تشغيل. عدم العودة ← Inactive: ليلاً auto-resolution حسب الدور، نقاشاً يُتجاوز، تصويتاً يعتبر ممتنعاً. لاعب واحد لا يستطيع تجميد Mafia أبداً.
- Leave صريح أثناء اللعب = إقصاء/خمول مع كشف الهوية حسب قواعد الإقصاء؛ لا مكافأة؛ لا عودة.
- كل المؤقتات تعتمد serverStartedAt/serverEndsAt — تلاعب المستخدم بساعة هاتفه لا يؤثر. العدّاد في العميل عرض فقط.

### 13.9 الأمان والقوة
Client لا يستطيع: تغيير دور/نتيجة/مؤقت/تصويت/قتل/حماية/إعلان فائز/منح مكافأة. كل Action بمعرّف idempotency — التكرار لا يضاعف التأثير (Kill/Protect/Investigate/Vote).

### 13.10 النهاية والمكافآف
عند تحقق الفوز: إيقاف المؤقتات ← قفل الأفعال ← حل الفائز ← كشف الأدوار النهائية ← حساب المكافآت ← نتيجة immutable ← رسالة نتيجة في الدردشة ← أرشيف.
- فائز = 10 عملات، خاسر = 2، لا تعادل. الإلغاء التقني = بلا مكافآت خسارة.

### 13.11 الأرشيف
Game ID، المجموعة، المنشئ، اللاعبون، الأدوار، الفريق، تاريخ الأطوار، الإقصاءات، نتائج التصويت، الفائز، المكافآت، المدة، الطوابع الزمنية. لا يُعرض خاص قبل النهاية.

### 13.12 الواجهة
الأكثر تجربة تفاعلية في Pubget — ليست واجهة عامة: مؤشر الطور، أجواء ليل/نهار، بطاقة الدور، شبكة اللاعبين (حي/ميت)، المؤقت، لوحة الأفعال، واجهة النقاش، واجهة التصويت، شاشة النتيجة، شاشة النصر. عربي كامل. كل حالة واجهة: تحميل/انتظار/خطأ/إعادة اتصال.

## المحور 14 — الأحداث (Events) — النظام الاجتماعي التفاعلي (ليس لعبة)

### 14.1 التعريف والنطاقات
محتوى/نشاط اجتماعي تفاعلي (تصويت، مقارنة، نظرية، تحدي، ترتيب، سؤال، توقع، كويز...) — ليس Game ولا يستورد Game Engine. النطاقات: Group · Multi-Group · Global.

### 14.2 الإنشاء
- مساران فقط: من دردشة المجموعة (+ ← إنشاء حدث) أو من Home (+ ← حدث ← اختيار النطاق: عام/مجموعات محددة).
- حد الإنشاء: حدثان/يوم (يشمل كل النطاقات؛ حدث متعدد المجموعات = إنشاء واحدة) — Server-side + منع race conditions.
- Builder: النطاق ← النوع ← المحتوى ← الخيارات/وسائط/إعدادات ← المدة ← معاينة إلزامية ← نشر. نشر مباشر دون موافقة مالك المجموعة.
- المدة: حد أدنى ساعة، حد أقصى 7 أيام. بدء فوري عند النشر إن لم يُحدد StartAt مستقبلي.

### 14.3 الحالات
`DRAFT → ACTIVE → ENDED → ARCHIVED` (+DELETED). النتيجة بعد الانتهاء Locked immutable — لا تعديل مشاركات ولا نتائج.

### 14.4 الرؤية
Group ← أعضاء المجموعة · Multi-Group ← أعضاء المجموعات المحددة (المنشئ عضو فيها كلها؛ حدث واحد لا نسخ؛ خروجه من مجموعة لا يحذف الحدث) · Global ← مستوى التطبيق (Home + Discovery + بحث + ملف المنشئ + إشعارات عند الحاجة). البحث يحترم الرؤية دائماً.

### 14.5 الظهور والاكتشاف
- Home: 3 أحداث فقط + "عرض المزيد" ← صفحة اكتشاف مستقلة (Pagination/Scroll لا نهائي/فلاتر/بحث؛ لا منتهية ضمن النشطة).
- Featured: ترتيب داخلي (حداثة، مشاركة، تفاعل، صلة، جودة منشئ، صلة المجموعة) دون تجاوز الرؤية.
- مداخل: Home (3) · عرض المزيد/الاختصار في القائمة العلوية (نفس الصفحة) · ملفي ← أحداثي · البحث.

### 14.6 صفحة الحدث
المنشئ، العنوان، الوصف، الوسائط، النوع، النطاق، الوقت المتبقي، حالة المشاركة، النتائج الحية (حسب النوع)، تعليقات (حسب النوع)، مشاركة، إبلاغ، أدوات المشاركة. لا خلط مع غرفة لعب.
- مستويات المعلومات الثلاثة: عامة حية (عدد المشاركين/نسب/وقت متبقٍ) · خاصة بالمشارك (مشاركته) · تحليلات المنشئ التفصيلية (من شارك، ماذا اختار، التوزيع، التفاعل) — لا يراها الآخرون.

### 14.7 الأنواع الـ12 (المغلقة) — لكل نوع منطق وواجهة خاصة
1. Poll: خيار واحد/متعدد (يحدده المنشئ)، 2+ خيار، نص + صورة اختيارية لكل خيار؛ تصويت واحد لا يتكرر ولا يُعدَّل بعد الإرسال؛ نتائج كنسب دون كشف المصوتين للعموم (المنشئ يرى التفاصيل).
2. Question: سؤال بلا إجابة صحيحة؛ إجابة نص (+صورة اختيارية). ليس كويز.
3. Theory: منشور نظرية (نصوص/صور)؛ تعليق/تفاعل/مناقشة/مشاركة؛ لا إجابة صحيحة ولا تصويت؛ تُؤرشف بالتفاعل.
4. Comparison: مقارنة عناصر أنمي صالحة (شخصيات/أنمي/قدرات...) من القواعد لا عناصر حرة؛ تصويت للطرف؛ نتيجة: أصوات/نسب/فائز.
5. Character Comparison: بحث شخصيتين من قاعدة الشخصيات (صورة/اسم/أنمي) ← تصويت ← نتيجة.
6. Anime Comparison: أنمي A/B ← تصويت ← نتيجة.
7. Ranking: قائمة عناصر (أنمي/شخصيات) ← المستخدم يرتبها Drag & Drop ← مشاركة واحدة فقط ← ترتيب نهائي مجمّع بعد الانتهاء.
8. Prediction: توقع ← المشاركون يختارون ← المنشئ يحل النتيجة لاحقاً (OPEN→RESOLVED→LOCKED؛ لا تعديل بعد الحل) ← إشعار نتيجة للمشاركين.
9. Quiz: عدة أسئلة، لكل سؤال صورة اختيارية + إجابات + إجابة صحيحة واحدة فقط؛ مؤقت لكل سؤال؛ صحيح = نقطة، خطأ = 0؛ نتيجة نهائية وترتيب وإجابات صحيحة؛ لا تعديل أسئلة بعد البدء.
10. Image Comparison: صور بعدد محدد ومعقول (صورة + عنوان/وصف اختياري) ← صوت لصورة واحدة ← نتيجة دون كشط هوية المصوتين.
11. Challenge: عنوان/وصف/قواعد/موعد نهائي/صورة مرجعية؛ المشاركة بـ Submission (نص/صورة)؛ لا حكم آلي مخترع — المنشئ يقرر الفائز؛ بعد التثبيت لا تغيير.
12. Open Discussion: موضوع/وصف/صورة اختيارية؛ نقاش كامل؛ لا إجابة/فائز/نقاط؛ يُؤرشف.

### 14.8 الإدارة والصلاحيات
- المنشئ: تحليلات، إنهاء مبكر، حذف، عرض المشاركين، حل النتيجة (للأنواع المطلوبة). لا يستطيع تغيير أصوات/إجابات/نتيجة مقفلة.
- إدارة أحداث المجموعة عبر صلاحية manageEvents ضمن مجموعته فقط؛ العضو العادي لا يدير حدث غيره.
- Multi-Group: المنشئ عضو في كل المجموعات المستهدفة.

### 14.9 الانهاء الآلي والإشعارات
- عند EndAt ينقله السيرفر إلى ENDED: قفل المشاركة ← حساب النتيجة ← قفلها ← أرشفة ← إشعارات ← تحديث الاكتشاف. لا يعتمد على فتح التطبيق.
- إشعار نتيجة لكل مشارك (للأنواع ذات نتيجة مشاركة — ليس Theory/Open Discussion بنفس الشكل) ← يفتح صفحة النتيجة: الحدث + مشاركته + النتيجة النهائية + إحصائيات.
- حدث من دردشة مجموعة: بطاقة نظام في الدردشة ← بعد الانتهاء تُنقل للأرشيف (البيانات لا تُحذف).
- إشعارات فقط للمهم: نشر ذي صلة، اقتراب الانتهاء عند الحاجة، انتهاء، نتيجة، تعليق/تفاعل مناسب، حل المنشئ. لا إشعار لكل مشاهدة.

### 14.10 الأداء والجودة
Pagination وLazy loading وCached metadata وThumbnails واستعلامات موجّهة؛ Home يحمّل 3 فقط؛ لا listeners مفتوحة؛ كل المشاركات idempotent (ضغطتا Submit = مشاركة واحدة؛ انتهاء الحدث أثناء الإرسال يحسمه السيرفر بطابعه الزمني دون حالة نصف مكتملة). كل شاشة: تحميل/فارغ/خطأ/منتهٍ/بلا صلاحية/مشاركت مسبقاً/نتائج مقفلة/إعادة محاولة.

## المحور 15 — نظام الريلز / الإيديتات (KIRARI)

الاسم الداخلي المعتمد: Kirari (キラリ) — قابل للتغيير من ثابت مركزي واحد (AppStrings.productReelsName) دون لمس أي نظام آخر. المستخدم يراه بالعربية "ريلز" وبالإنجليزية "Reels".

### 15.1 الهوية والمحتوى
- منصة short-form anime creativity داخل Pubget — ليست TikTok عربياً: أرقى، اجتماعية، مرتبطة بالاحترام/المعجبين وAnime Hub والـ Social Graph.
- المحتوى: فيديو عمودي قصير (3 ثوانٍ – 60 ثانية) فقط — لا سلايدshow صور (الصور لها أنظمتها).
- الهوية الأساسية أنمي/ثقافة يابانية: edits, AMV, مشاهد, شخصيات, لحظات, ميمز, تحولات, مقارنات مرئية, نظريات مرئية, توصيات, مراجعات, كوسبلاي, إبداعات أصلية مستوحاة. الإبداع الواسع مسموح والهوية تبقى أنمي-بوبجيت.

### 15.2 إنشاء المحتوى (Flow)
`إنشاء (+ ← ريلز) ← اختيار فيديو من الجهاز ← تحرير ← Metadata ← معاينة ← نشر`.
- الاختيار من المعرض فقط في هذا الإصدار (لا تسجيل كاميرا). فحص: المدة، الصيغة، الحجم (≤ 500MB)، العمودية.
- محرر MEDIUM/SMART/FAST: قص (بداية/نهاية) · إطار/قصّاصة · سرعة محدودة · مستوى الصوت الأصلي · تحكم صوت مضاف · نص بسيط فوق الفيديو بتوقيت بسيط · فلاتر/تأثيرات خفيفة لا تضرب الأداء · اختيار الغلاف · معاينة. ممنوع محرر ثقيل، وممنوع تحرير سطحي عديم القيمة.
- الغلاف (Cover): إطار من الفيديو أو صورة من الجهاز — مع معالجة نسبة العرض/القصّ/منطقة الأمان/معاينة (لا صور مشوهة أبداً).

### 15.3 Metadata غنية (إلزامية عند النشر)
Caption · Hashtags · Anime tags (بحث/اقتراء تلقائي من قاعدة الأنمي — لا كتابة يدوية حرة) · Character tags (كذلك) · إشارات مستخدمين (Mentions) · صوت · فئة محتوى · مرجع مجموعة عند المشاركة · مرجع حدث عند الارتباط. إضافتها سهلة وسريعة من شاشة النشر.

### 15.4 نظام الصوت
1. الصوت الأصلي للفيديو. 2. Audio Library داخل Pubget (محتواها الأولي: أصوات منشورة أصلاً من فيديوهات المستخدمين — لا ندّعي امتلاك موسيقى مرخصة). 3. Reuse Audio من أي ريلز. 4. صفحة الصوت: الاسم، صاحبه، عدد الاستخدامات، الريلز المستخدمة له، زر استخدام، feed للمستخدمين. 5. إسناد واضح للمصدر. 6. Original Audio مرتبط بصاحبه.
- Provider-agnostic: معالجة الدمج Server-side عبر MediaService abstraction (الجهاز يرفع الفيديو والصوت منفصلين) — قابلة لربط مزود مرخص مستقبلاً دون إعادة بناء.

### 15.5 تجربة المشاهدة (Reel Viewer موحد)
- Full-screen عمودي، تشغيل تلقائي، انتقالات ناعمة، Preloading، Caching ذكي، جودة تكيفية (360p/540p/720p تُختار تلقائياً حسب الشبكة والجهاز والتخزين المؤقت — خفض الجودة عند الضعف بدل التوقف).
- كل نقاط الدخول تفتح نفس المشاهد الموحد: Home، Trending، البحث، الملف الشخصي، الصوت، الهاشتاغ، الأنمي، الشخصية، الرابط المشارك، محتوى صانع، ريلز مشاركة في مجموعة/خاص.
- من الملف الشخصي: دخول سياق صانع محدد (تنقّل ضمن ريلز نفسه).

### 15.6 واجهة الفيديو (Pubget UI لا TikTok UI)
- بنفسج ملكي + ذهبي بذكاء، داكن/فاتح متقنان، واجهة لا تغطي الفيديو، هرمية واضحة تُظهر: الصانع (صورة/اسم/رتبته حيث يلائم دون سرقة انتباه) · زر الاحترام/المعجب (Bottom Sheet: الهوية، العلاقة الحالية، إعطاء Respect، المستوى، حالة المعجب، شرح مبسط — ≥5 يجعله من المعجبين) · Caption · Hashtags · سياق الأنمي/الشخصية · الصوت · أدوات التفاعل.
- التفاعلات: إعجاب (نقرة مزدوجة بحركة Pubget مميزة + Haptic) · تعليق · حفظ · مشاركة (خاص/مجموعة/خارجي) · احترام/معجب · إبلاغ · غير مهتم · حظر · كتم. Gestures + BottomSheets + Micro-interactions خفيفة — لا ثقل.

### 15.7 التعليقات
نص · ردود متداخلة · إعجاب تعليقات · إشارة مستخدمين · حذف تعليقي · إبلاغ · حظر/كتم · تثبيت تعليق للصانع · مؤشر "الصانع" على تعليقاته · ترتيب (أحدث/أعلى إعجاباً) · Pagination · سلوك شبه لحظي · ملصقات كتعليقات (من نظام الملصقات الموجود — سريع جداً). Optimistic where safe، منع التكرار، Retry، حالات فارغ/خطأ.

### 15.8 الخلاصات الثلاث (Feeds)
For You (موصى به) · Following (المعجبون/الرسم الاجتماعي) · Trending — كلٌّ بمنطق ترتيب مختلف حقيقي، ليست tabs شكلية.

### 15.9 محرك التوصيات (الأهم)
- ممنوع "most likes = recommended". إشارات سلوك: مدة المشاهدة، نسبة الإكمال، المشاهدة الجزئية، سرعة التخطي، الإعادة، التوقفات، مشاركات، حفظ، إعجاب، تعليقات، ردود، زيارات الملف، تحول معجب، تفاعلات صوت/هاشتاغ/أنمي/شخصية، سلوك بحث، ملاحظات سلبية، غير مهتم، إخفاء، حظر، كتم.
- إشارات محتوى: تفضيلات أنمي/شخصيات/نوع/هاشتاغات/صوت/صانع/موضوع. إشارات اجتماعية: المعجبون، الأصدقاء، المجموعات، أعضاء مجموعاتي، أذواق مشابهة. حداثة: اكتشاف جديد، تفاعل حديث، سرعة التفاعل. جودة: إكمال، احتفاظ، تفاعل ذو معنى، بلاغات.
- استغلال 70–90% + استكشاف 10–30% (نسب قابلة للمعايرة لا نص صلب). تنوُّع مضبوط: منع 20 ريلزا من نفس الأنمي متتالية (قبعات تنوع حسب أنمي/صانع/شخصية/صوت/موضوع).
- Kirari هو مصدر رئيسي للـ Social Recommendation Graph: مشاهدة ريلز ون بيس ← اهتمام ← توصية محتوى/مجموعات/أحداث/صنّاع مترابطة — مع بقاء الباب مفتوحاً لاكتشاف اهتمامات جديدة.
- إعادة الضبط: زر في الإعدادات يصفّر ملف التوصية (مع تأكيد).

### 15.10 Trending
سرعة التفاعل (Velocity) لا الأرقام المطلقة: مشاهدات، إكمال، مشاركات، حفظ، تعليقات، إعادات، حداثة، تنوع الصنّاع، تغذية سلبية، جودة. مساحة "ما يحدث الآن" بهوية Pubget.

### 15.11 الهاشتاغات
صفحة لكل هاشتاغ: العنوان، إجمالي الاستخدام، المحتوى الحديث/الرائج، أفضل الريلز، هاشتاغات مرتبطة، أنمي/شخصيات ذات صلة. تدخل في التوصيات (لا نص فقط).

### 15.12 المشاهدات والإحصاء (تعريفات إلزامية)
- Impression ≠ View ≠ Qualified View ≠ Completion ≠ Replay.
- View تُحسب بعد عتبة مشاهدة معقولة (≥ 3 ثوانٍ فعلية)، مع منع: الفتح العرضي، التكرار السريع، الريفريش فارمنغ، الأنماط الآلية. منع تضخيم المشاهدات.
- Rewatch إشارة قوية (شاهد 95% ثم أعاد = إيجابي قوي يدخل التوصية).
- العدادات (likes/comments/shares/saves/views) Server-safe — لا increment أعمى من العميل.

### 15.13 خط الرفع والنشر
- نشر ← العودة فوراً للتجربة ← مؤشر رفع عام (Global Upload Manager) يعرض: Uploading → Processing → Preparing → Published / Failed. لا حظر للواجهة أثناء الرفع؛ قائمة انتظار تدعم رفعاً واحداً فعالاً (حد 10 ريلز/يوم).
- Resilience: شبكة ضعيفة، انقطاع مؤقت، خلفية التطبيق، Retry، فشل، مهلة — لا فقدان للفيديو ولا metadata، Retry يدوي، لا نشر مزدوج أبداً (idempotency keys).
- Pipeline سيرفر: رفع ← تحقق ← ضغط/معالجة ← توليد غلاف ومعاينات ← معالجة جودات ← فحوص أمان/اعتدال ← جاهز ← متاح.

### 15.14 الأداء (REQUIRED)
تشغيل الفيديو الحالي فقط + preload منطقي للتالي؛ dispose للـ controllers؛ لا مشغلات متعددة نشطة؛ لا rebuild للـ feed كله عند إعجاب واحد؛ Pagination؛ Cache للغلاف؛ فك ترميز فعال؛ Retry شبكي. الجهاز المتوسط أولاً — لا افتراض أجهزة قوية.

### 15.15 التكاملات
- Anime Hub: ريلز مرتبط بأنمي ← انتقال لصفحة الأنمي (ريلز/صنّاع/محتوى مرتبط)؛ مرتبط بشخصية ← سياقها. والعكس: من صفحة أنمي/شخصية ← اكتشاف ريلز مرتبطة.
- الملف الشخصي: تبويب ريلز بشبكة معاينات ← المشاهد الموحد بسياق الصانع.
- المجموعات والخاص: مشاركة ريلز كبطاقة غنية (غلاف/صانع/وصف مختصر/فتح/صوت) — مرجع لا نسخة مكررة. الريلز محتوى مستقل لا يُنشر "داخل" مجموعة كمالك.
- الاحترام/المعجبون: زر الصانع = نظام Pubget (لا Follow).

### 15.16 الإشعارات (ذكية)
إعجاب/تعليق/رد/إشارة/مشاركة مناسبة/محطة احترام أو معجب جديد/نشاط مهم لصانع. تجميع ذكي: "3 مستخدمين أعجبوا بفيديوك" بدل 3 إشعارات؛ التعليقات المهمة لا تضيع. لا إشعار لكل انطباع. الضغط ← الوصول المباشر للسياق.

### 15.17 تحليلات الصانع (Dashboard)
لكل ريلز: مشاهدات، مشاهدون فريدون (إن أمكن)، وقت المشاهدة، متوسط المدة، نسبة الإكمال، الإعادة، إعجابات، تعليقات، ردود، مشاركات، حفظ، معجبون جدد، احترام مستلم، زيارات الملف، مصدر الترافيك، أداء الهاشتاغات/الصوت، منحنى الاحتفاظ (إن أمكن). Overview: إجماليات، أفضل ريلز، رائج، نمو، أعلى أنمي/شخصيات/هاشتاغات/أصوات. لا أرقام وهمية.

### 15.18 الحالة والاعتدال والحقوق
- State Machine لكل ريلز: draft ← uploading ← processing ← moderation_pending ← ready ← published ← failed ← restricted ← removed ← archived. لا فوضى booleans.
- إبلاغ (ريلز/تعليق/صوت) بتصنيفات واضحة · حظر · كتم · غير مهتم (يقلل النوع، يخفي الريلز، لا يعاقب الصانو بلا مبرر، قابل للعكس من الإعدادات).
- حقوق نشر: بنية تدعم بلاغات، takedown، حالات محتوى، قيود — دون ادعاء امتلاك حقوق الأنمي/الموسيقى.
- حذف الصانع: يختفي من الخلاصات والملف والبحث والهاشتاغات وصفحات الصوت؛ الروابط تعرض حالة مناسبة؛ تحفظ بيانات التدقيق.
- مشاهدة ضيف: المحتوى العام يُشاهد دون تسجيل؛ التفاعل (إعجاب/تعليق/حفظ/احترام/مشاركة خاص/معجب) يتطلب حساباً.
- المسودات: تحفظ مرجع الفيديو + كل metadata + الغلاف + إعدادات التحرير — دون رفع للتخزين العام.

### 15.19 مخطط البيانات (مبادئ)
Collections/subcollections مستقلة (لا تعليقات ولا إعجابات داخل مستند الريلز)، Pagination، Indexes، Security Rules. الأحداث الداخلية: impression/started/completed/skipped/rewatched/liked/... batching مضبوط لا إغراق.

### 15.20 معايير القبول (غير مكتمل إذا)
مشغّل فقط = فشل · ترتيب زمني = فشل · تعليقات بدائية = فشل · لا صوت/صفحة صوت = فشل · لا هاشتاغات = فشل · لا تكامل Anime = فشل · لا Social Graph = فشل · احترام/معجب ناقص = فشل · تحليلات وهمية = فشل · رفع يحجب UI = فشل · ضعف شبكة يوقف الفيديو = فشل · memory leaks = فشل · تكرار أفعال ممكن = فشل · بقاء القديم المتعارض = فشل · شكل TikTok نسخ = فشل · لا هوية Pubget = فشل.

## المحور 16 — Anime Hub (فضاء الأنمي — معلومات وقوائم وتقييمات، بلا بث حلقات)

### 16.1 المبدأ الحاكم
لا يوفر المشاهدة ولا روابط حلقات ولا سيرفرات ولا scraping. Anime Hub = اكتشاف منظم ومعلومات وقوائم وتقييمات وربط اجتماعي. أي "مشاهدة حلقة" داخله = خرق فادح.

### 16.2 مصادر البيانات (Provider-agnostic)
- `AnimeRepository` abstraction خلفها: Jikan API (MyAnimeList) مصدر أساسي + AniList GraphQL بديل، مع Cache داخلي في Firestore يمنع الضغط على المصادر ويمنع انهيار التطبيق عند تعطلها (البيانات المخزنة تخدم كـ fallback أنيق).
- الصور تُعرض مع Cache صارم (Thumbnail/Medium/Full حسب الحاجة).

### 16.3 الاكتشاف
الرئيسية: الموسم الحالي · قادم · الأكثر شعبية · الرائج (Velocity) · الأعلى تقييماً · إصدارات جديدة. تصفح: التصنيفات (Genres) · الاستوديوهات · الشخصيات الشعبية. Lazy loading/Pagination (دفعات 20).

### 16.4 صفحة الأنمي
بوستر، العنوان (عربي/إنجليزي/ياباني/بدائل)، الوصف، الاستوديو، التصنيفات، الحالة، سنة الإصدار، عدد الحلقات، المعلومات، التقييم، الشخصيات (صور مصغرة + مؤدو الأصوات)، الأعمال المرتبطة، و Tabs منظمة (معلومات/شخصيات/مرتبط).
الأقسام الاجتماعية Pubget:
- رأي المجتمع: تقييمات ومراجعات المستخدمين، نقاشات، آراء.
- ريلز مرتبطة: إيديتات/مقاطع مرتبطة بالأنمي (من وسوم Kirari) — بطاقات فاخرة.
- مجموعات مرتبطة: مجموعات تناقش هذا الأنمي ← اكتشاف وانضمام.
- أحداث مرتبطة: أحداث حول هذا الأنمي.
- أعمال خاصة مرتبطة: Fan Works مبنية على هذا العالم.

### 16.5 صفحة الشخصية
الصورة، الاسم، الأنمي المنتمية، المعلومات، الشعبية (محسوبة من عدد المفضلين لدى المستخدمين)، تقييم المستخدم لها + إضافتها للمفضلة + ترتيبها، قسم فيديوهات/ريلز مرتبطة بها، أعمال خاصة مرتبطة، نقاشات المجتمع حولها.

### 16.6 قوائم المستخدم (مرتبطة بالملف)
قوائم مغلقة: أشاهده الآن · أكملته · أخطط لمشاهدته · أسقطه · معلّق + المفضلة. وعلاوة عليها: قوائم مخصصة يصنعها المستخدم بحرية (مثال: "أنميات ترفع الضغط"). كل قائمة قابلة للعرض في الملف (حسب الخصوصية).

### 16.7 التقييم
- تقييم داخلي 1–10 لكل أنمي؛ المتوسط يُحسب Server-side من تقييمات المستخدمين ويُحدَّث فوراً.
- تقييم الشخصيات (إعجاب/تقييم/ترتيب).
- إحصاءات مجتمعية: الأعلى تقييماً، الأكثر في قوائم المستخدمين، شخصيات هذا الموسم...

### 16.8 البحث والفلترة
Fuzzy Search (عربي/إنجليزي/ياباني/بدائل — يغفر الخطأ الإملائي) + فلاتر (تصنيف + حالة + سنة + تصنيف عمري + استوديو...). نتائج تجمع: أنمي ← شخصيات ← مجموعات ← ريلز ← أحداث ← أعمال خاصة.

### 16.9 التوصيات
من: قوائم المستخدم، تقييماته، مفضلاته، تفاعلاته مع Kirari، مجموعاته، أحداثه — مع احترام الخصوصية. لا "شاهدت ناروتو، شاهد ناروتو مجدداً"؛ اكتشاف مترابط (أنمي ← مجموعة ← صانع ← حدث ← عمل خاص).

### 16.10 التوسع المستقبلي
البنية لا تمنع Manga/Manhwa/الثقافة اليابانية كـ Domains لاحقة — دون بنائها الآن.

## المحور 25 — ميزانية الأداء

- لا rebuild لشاشة كاملة عند تغير صغير؛ Lists افتراضية؛ Pagination إلزامية؛ Cache صور (غلاف/وسط/كامل)؛ لا تنزيل ملفات أصل عندما يكفي مصغّر؛ Video: غلاف + preload للتالي + dispose للسابق؛ لا listeners مكررة؛ فصل الثقيل عن UI thread؛ تحميل خلفي لا في الإقلاع.
- أهداف إحساسية: فتح شاشة ≤ 300ms، تمرير خلاصة بلا تقطيع على جهاز متوسط، قراءات Firestore مضبوطة بتقارير.

## المحور 26 — الاختبارات ومعايير القبول

- لكل Domain: Unit (منطق) + Widget (سلوك واجهة) + Integration (تدفقات) + Rules/Functions عبر Firebase Emulators + سيناريوهات Multi-user حيث يلزم + Regression.
- معايير قبول خاصة موجودة داخل كل محور (Games §12، Mafia §13، Events §14، Kirari §15). لا "تم" بلا اجتيازها.
- أدوار: analyze = 0 أخطاء؛ tests ناجحة؛ build ناجح — قبل أي تسليم.

## المحور 27 — سير العمل مع GitHub (إلزامي على الوكيل)

1. كل مهمة = فرع مستقل `feature/<المحور>-<الوصف القصير>` من آخر main نظيف.
2. قبل فتح PR إلزامياً: `flutter analyze` (0 issues) · `flutter test` (كلها ناجحة) · اختبارات Firestore/Storage Rules عبر Emulator إذا لُمست القواعد · `flutter build` ناجح · فحص يدوي للتعديلات (لا ملفات مشوهة، لا تنسيق مكسور، لا imports ميتة).
3. ممنوع على الوكيل الدمج أو الدفع المباشر لـ main — المالك وحده يدمج من صفحة Pull Request.
4. تقرير إلزامي بالقالب (في برومبت التشغيل) + رابط الـPR الكامل الجاهز للدمج.
5. أي تعديل على Security Rules: اختبارات Emulator إلزامية مرفقة في التقرير، ولا يُقترح أي إضعاف أمان — عند الحاجة: توثيق المخاطرة والتوقف.
6. لا commits عملاقة غامضة؛ commits صغيرة موضوعية واضحة.

## الملحق أ — قواعد الحكم (عندما لا تغطي الوثيقة نقطة)

اختر الحل الأكثر: stable · scalable · performant · secure · maintainable · متوافق مع Flutter/Firebase ومع بنية Pubget. لا تغيّر اتجاه المنتج. إن تعارض قرار مع الوثيقة: الوثيقة تفوز. إن غيّرت قراراً أنتجياً مفترضاً: وثّقه في تقريرك بوضوح. توقف وأبلغ فقط عند: تضارض حقيقي داخل الوثيقة، هجرة بيانات مدمرة، إضعاف أمن لا مفر منه، أو اعتماد خارجي غير متاح.
